## 核心洞察

容器的本质是资源隔离，通过文件隔离(chroot/pivot_root)、访问隔离(Namespaces)和资源隔离(cgroups)三层机制，实现了轻量级的进程隔离。

## 详细笔记

### 1. 容器本质：资源隔离而非部署工具

> 核心认知：容器技术最初目标是安全隔离(开发/测试环境防护、蜜罐系统)，后期才演变为部署载体。
>
> 架构启示：当讨论容器化时，首要考虑隔离需求强度(安全边界/故障域)，其次才是部署便利性。

**隔离价值级别**：

| 隔离层级 | 业务价值         | 典型场景          | 架构风险         |
| ---- | ------------ | ------------- | ------------ |
| 强隔离  | 敏感数据保护、合规性   | 金融核心系统、医疗数据处理 | 资源开销大，运维复杂度高 |
| 弱隔离  | 开发测试环境、无状态服务 | 前端应用、缓存服务     | 隔离不足可能导致级联故障 |

### 2. 三层隔离机制演进

**文件隔离：从chroot到pivot_root**

| 技术         | 诞生时间        | 原理      | 局限性           | 现代应用           |
| ---------- | ----------- | ------- | ------------- | -------------- |
| chroot     | 1979(UNIX)  | 锁定进程根目录 | 无法隔离非文件资源     | 仅用于基础环境隔离      |
| pivot_root | 2000(Linux) | 切换根文件系统 | 仍依赖其他机制实现完整隔离 | Docker/LXC的底层基础 |

**访问隔离：Namespaces的演进**

| NAMESPACE类型 | 隔离资源         | 架构价值              | 注意事项           |
| ----------- | ------------ | ----------------- | -------------- |
| PID         | 进程ID空间       | 独立进程树，无感知宿主机进程    | 0号进程由容器内init管理 |
| Network     | 网络设备/端口/路由表  | 网络策略隔离            | 需配合CNI插件实现互通   |
| User        | UID/GID映射    | 容器内root ≠ 宿主机root | 关键安全增强，避免提权    |
| Cgroup      | cgroup挂载点可见性 | 资源视图隔离            | 仅Linux 4.6+支持  |

**资源隔离：cgroups的两代演进**

| 特性       | cgroups v1(2008) | cgroups v2(2016) | 架构影响           |
| -------- | ---------------- | ---------------- | -------------- |
| 层级结构     | 多树状结构(每资源类型独立)   | 统一单树结构           | v2资源分配更精确，避免冲突 |
| CPU控制    | shares + quota   | 统一权重+最大限制        | 混合负载场景更可控      |
| 内存OOM处理  | 全局LRU回收          | 按cgroup分组回收      | 避免单服务故障拖垮整个节点  |
| Docker支持 | 完整支持             | 部分支持(需高版本)       | 生产环境需验证资源限制有效性 |

> 资源隔离红线：
> 必须配置：`memory.limit_in_bytes` + `cpu.cfs_quota_us`
> 禁止：无限制容器运行在生产环境。

## 相关思考

容器的三层隔离机制是其轻量级特性的基础，理解这些机制对于正确使用容器和排查容器问题至关重要。cgroups v2的统一架构是未来的发展方向。
