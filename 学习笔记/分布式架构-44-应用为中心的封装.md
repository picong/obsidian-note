## 核心洞察

Kustomize提供了轻量级的配置管理能力，而Helm则是Kubernetes的软件包管理器，提供了完整的应用生命周期管理。两者各有侧重，在实际应用中常联合使用。

## 详细笔记

### 1. 应用封装的核心矛盾

传统容器封装的问题：
- Docker封装的只有单服务镜像。
- Kubernetes封装的是服务资源配置。
- 但没有载体封装完整的应用生命周期(安装、更新、回滚、版本、依赖等)。

因此需要真正做到：
- 开发关注应用逻辑
- 运维关注部署策略
- 平台团队关注资源调度

### 2. Kustomize

**核心思想**
> "用配置文件管理配置文件"
> 目标：解决不同环境生成不同部署配置的繁琐性。

机制：
- 把资源按不可变(Base)和可变(Overlay)分离。
- 多环境基于Base派生配置(类似Docker分层镜像)。
- 编译期自动生成最终YAML包。

**价值**
- 就近管理YAML，不需要额外DSL。
- 可在不同环境生成不同打包(生产/调试/不同客户版本)。
- 已集成到`kubectl`，不需要独立工具。

**局限**
- 本质只是"减少重复写YAML"。
- 应用生命周期能力不足：
  - ❌ 更新
  - ❌ 回滚
  - ❌ 多版本
  - ❌ 多实例
  - ❌ 依赖管理
  - ❌ 部署跟踪

因此：
> Kustomize = 轻量级配置扩展工具，不是应用管理平台。

### 3. Helm(Chart)

**设计定位**
> "Kubernetes的软件包管理器"

类似Linux：
```
APT -> DEB
YUM -> RPM
Helm -> Chart
```

目标：
- 提供应用安装/升级/回滚/卸载/多版本管理
- 管理依赖
- 提供应用仓库(Repository)

**Chart目录结构示例**
```
WordPress
├── templates/*.yaml
├── values.yaml
├── requirements.yaml
└── Chart.yaml
```
- Chart.yaml：应用元数据(名称、版本、描述)
- values.yaml：默认可配置项，部署时可覆盖
- templates/：Kubernetes资源模板，变量在渲染时注入

**机制优势**
- 一条命令完成安装部署
- 支持回滚
- 支持依赖管理
- 支持图形化UI
- 社区有中央仓库(也可自建)

**Kubernetes 与 Linux 不同的地方**

最大区别：
- Linux应用通常只装一份
- Kubernetes同一应用常常多实例部署

因此引入：Release
> Helm每次安装Chart都产生一个独立实例：

```
MySQL v1 → Release #1
MySQL v1 → Release #2（另一副本）
```

对无状态应用足够，但对有状态应用(DB、缓存、队列)仍需要更强能力，需要Operator & OAM。

## 相关思考

Kustomize和Helm各有侧重，Kustomize适合简单的配置管理，Helm适合复杂的应用生命周期管理。在实际应用中，两者常联合使用。
