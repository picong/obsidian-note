## 核心洞察

Operator通过自定义资源和控制器模式，将复杂应用的运维逻辑封装在代码中，是应对有状态应用封装运维的最可行方案。OAM通过关注点分离，简化了云原生应用的配置管理。

## 详细笔记

### 1. Operator(针对有状态应用)

Operator是一种封装、部署和管理Kubernetes有状态应用的方法，尤其适用于复杂应用的运维能力封装。

**核心理念与机制**
- 定位：不仅仅是一种工具或系统，而是一种管理方法。
- 基础：基于Kubernetes的自定义资源(Custom Resource Definition, CRD)。Operator定义了一种更高层次的资源(如 kind: Elasticsearch)。
- 实现：通过实现自定义Kubernetes控制器(Controller)，将Kubernetes的控制器模式从面向内置资源扩展到面向自定义资源。
- 工作方式：监视自定义资源(CR)的类型，并执行特定于应用的低级操作(Low-Level Operations)，以确保当前状态与用户在CR中定义的理想状态/高级指令(High-Level Directives)相符。

**有状态应用与Operator**
- 有状态应用特征：自身持有运行时所需数据，外部依赖资源(如特定存储位置)，多个实例间可能有特定的拓扑关系和顺序关系(如数据库集群的选主)。
- Kubernetes内置支持：StatefulSet解决了Pod重建后状态保留的需求，提供了顺序创建/销毁、稳定网络名称、稳定持久存储等特性。
- StatefulSet局限性：只能实现创建、删除、扩缩容等基本操作，不支持复杂的、特定于应用的运维操作(如备份/恢复、创建/删除索引、调整平衡策略等)。
- Operator的价值：
  - 将复杂应用的运维逻辑通过程序编码封装在控制器中。
  - 允许用户使用简洁的"高级指令"(如仅定义ES版本和节点数)替代复杂的Kubernetes"低级操作"（冗长的Service，ConfigMap，StatefulSet YAML)。
  - 可以实现StatefulSet无法支持的复杂运维功能(如数据备份/恢复)

**优势与现状**
- 优势：
  - 遵循Kubernetes基于资源和控制器的设计原则。
  - 突破了Kubernetes内置资源的表达能力限制，更加灵活。
  - 符合DevOps一体化理念，用代码来描述复杂状态比配置文件更简单。
- 现状：
  - 开发门槛较高，通常由专业的平台开发者完成(代码量较大)。
  - 已成为应对有状态应用封装运维的最有可行性方案之一，生态正在成熟。

### 2. OAM(开放应用模型/Open Application Model)

OAM是阿里云和微软联合发布的云原生应用标准定义与架构模型，旨在解决云原生应用配置的复杂性。

**核心思想：关注点分离**

OAM的核心是将不同角色的关注点分离，以简化各自的工作：
- 开发人员：关注业务逻辑和Components。
- 运维人员：关注程序的平稳运行和Traits组合。
- 平台人员：关注基础设施能力和稳定性，提供OAM的解释能力。

**OAM的核心概念(自定义资源)**

| 概念   | 英文                        | 关注方       | 职责/含义                                                 |
| ---- | ------------------------- | --------- | ----------------------------------------------------- |
| 服务组件 | Component                 | 开发人员      | 抽象出业务逻辑元素，如应用名、镜像、运行参数等。                              |
| 工作负荷 | Workload                  | 开发人员/平台人员 | 决定该应用的运行模式(如是否长期运行、是否可复制)。每个Component设定Workload类型。    |
| 运维特征 | Trait                     | 运维人员      | 封装模块化的运维能力(如日志收集、水平扩容、负载均衡)。可重复利用，作用于特定Workload类型。    |
| 应用边界 | Application Scope         | 运维人员      | 将Components划分到一或多个应用边界中，便于统一做配置、限制、管理(非必须)。           |
| 应用配置 | Application Configuration | 运维人员      | 将Components(必须)和Trait(必须)以及Scope(非必须)组合并实例化，形成完整的应用配置 |

**优势与前景**
- 优势：
  - 解耦复杂的All-in-One配置，实现不同角色的专业化分工协作。
  - 简化了单个角色的关注内容，提高了聚焦度和专业度。
  - 是业界首个云原生应用标准定义与架构模型。
- 前景：很大程度上取决于云计算厂商的支持力度，因为OAM的自定义资源通常由基础设施负责解释和驱动。
- 主要参考实现：Crossplane、阿里云主导的KubeVela。

## 相关思考

无论是Kustomize、Helm(无状态应用为主)，还是Operator、OAM(有状态应用为主)，目前应用封装领域的明确共识是：以应用为中心的理念。各种技术并非完全重复，在实际应用中往往会联合使用。
